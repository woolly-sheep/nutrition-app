# 料理プリセット（料理名でまとめて登録・記録）

- 日付: 2026-07-25
- ステータス: 採用
- 関連: [[decision-20260724-supplement-products]]（製品プリセット）/ [[decision-20260715-mvp-data-api-simplification]]
- 対応 issue: #29（料理名でどの食材がどのくらい使用しているか紐づけられるか）

## 背景

ユーザー要望「料理名でどの食材がどのくらい使用しているか、料理名で紐づけたい」。
毎回同じ食材の組み合わせ（例：いつもの朝食）を1品ずつ検索して入力するのは手間。
可否をユーザーに確認したうえで**料理プリセット方式**の採用が決定した。

## 決定

料理 = **名前 ＋ 食材（食材ID＋グラム）のリスト**。製品プリセット（サプリ）と同型で、
食品側に用意する。

### 栄養値は保存しない（重要）
サプリ製品プリセットは自己申告の成分値を保存するが、料理の食材は**すべて凍結seedの
実食品**。したがって料理は栄養値を一切保存せず、**表示・記録のたびに seed から算出**する。
これにより料理が常に公式表と整合し、保存値が公式値から乖離する余地をなくす
（公式seed値の手編集・再計算の禁止に抵触しない）。

### データ・API
- `data/recipes.json`（他ストアと同じ・ローカル・gitignore・ログ非出力）。id は `rec_`。
- `GET /api/recipes` … 保存した料理に**食材の表示名・食材別kcal・料理合計kcal**を付与して返す
  （`listRecipeViews`・すべて seed から算出）。
- `POST /api/recipes` … name＋items。items の検証は**食事保存と同じ `validateItems` を再利用**
  （既知の seed 食品・g>0・上限）。不正時はフィールドコードのみで料理名を漏らさない。
- `DELETE /api/recipes/{recipe_id}` … 未知idは404。
- バックアップ（GET/POST /api/backup）に `recipes` を追加。旧バックアップ（配列なし）も復元可。

### UI（記録タブ `MealEntryScreen`）
- **「料理から追加」**セクション … 登録済み料理を一覧（品数・推定kcal）。「＋追加」で
  中身の食材を**現在の下書きに展開**（1タップ・自動保存はしない＝いつもの食事と同方針）。「削除」も。
- **「料理として登録」** … 下書きに食材があるとき、料理名を付けて現在の内容をそのまま料理化。
  （build via 検索 → 名前 → 登録、が最短動線）。

## 影響

- テスト 201 → 209（saveRecipe・listRecipes enrichment・backup 往復＋不正食品の8件）。
- 契約 23 → 26 オペレーション（`check:api-contract` pass）。
- 既存データ・凍結seed・栄養計算/判定ロジックは不変（料理は既存の meal 保存経路に載るだけ）。

## 却下した代替案
- **料理を新規 seed 食品として登録**（合成食品の栄養値を保存）: seed 改変・値の乖離リスク・
  出典を示せないため却下。料理は「実食品の組み合わせ」に限定する。
